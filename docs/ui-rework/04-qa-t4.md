> 验收人：QA 严过关（独立复测，工程师数值仅作对照）｜ 时间：2026-11-17 ｜ 服务 `localhost:3000` 全程未重启

## 0. 环境与方法（含两个必踩的坑）

| 项 | 做法 |

| 隔离 | **每个测量点一个全新 Chrome 实例**（独立 `--user-data-dir` + 独立调试端口），测完 `taskkill /T /F` + 删 profile。未执行 `localStorage.clear()` |
| 单次导航 | 每实例只 `Page.navigate` 一次，其余为 in-app 点击 |

| 卡片判定口径（与 02-baseline / 03-qa-t3 完全一致） | 排除 `table/thead/tbody/tr/td/th/ul/li/option`；要求 (`border-width>0 且 style≠none` **或** `box-shadow≠none`) **且** `border-radius≥4px` **且** 背景不透明；统计单位为"直接含 ≥2 字文本节点的元素"，沿 `parentElement` 上溯计数 |
| 遮挡修正 | 本轮新增 `el.checkVisibility({checkVisibilityCSS, contentVisibilityAuto})` 作为"绘制可见"判定，用于剥离 `<details>` 折叠内容，得到「结构口径」与「绘制口径」两组数 |
| 轮询验证 | `Network.requestWillBeSent` 记 `/api/parttime/queue` 时间戳；切后台用 `Target.createTarget + activateTarget`（`Emulation.setPageVisibilityOverride` 本机 Chrome **不支持**，调用报错） |
| 错误态构造 | `Network.setBlockedURLs(['*/api/workbench/deduction-profiles/*'])`，**未触发任何写操作/真实登录** |

### 0.1 两个坑（会直接产出假数据，建议写进团队 QA 手册）

1. **≤1024 侧栏只剩图标，按 `innerText` 点侧栏必然失败。** 首轮把 1024 档测成了采集页（`.wbx-empty` 取自非活动视图，实测 0×0）。修法：改用 `textContent` 匹配 + 点击后用页面标记（如 `.pq-workbench` 高度 >100）校验，失败重试。
2. **非活动视图是"已挂载但 0×0"**，`querySelector` 能命中但不可见 —— 所有几何测量必须先确认页面标记可见，否则会拿到 0 值当真值。

另：`<details>` 折叠时其内容 `getBoundingClientRect()` **仍返回非零尺寸**（内容不被绘制、`innerText` 为空），因此"结构口径"与"绘制口径"必须分开报，否则会把隐藏内容算成可见缺陷。

| 指标 | 值 |
| --- | --- |
| 卡内内容簇（icon → actions） | **153px**（icon y=384 h40 / 标题 y436 h21 / 描述 y469 h21 / 按钮 y505 h32） |

## 3. 扣款规则卡片嵌套（第 3 条）—— 不通过

### 3.1 两组口径的实测

| 口径 | 状态 | 最大嵌套 | ≥3 层文本节点 | ≥2 层节点 |
| --- | --- | --- | --- | --- |
| **结构口径**（同基线，不做可见性过滤） | 折叠 / 展开 | **3** | **200** | 612 |
| **绘制口径**（`checkVisibility`,剥离折叠内容） | 默认折叠 | **2** | **0** | 3 |
| **绘制口径** | 展开站点例外表 | **3** | **200** | 612 |
| 基线（02-baseline） | — | 4 | **611** | — |
| 工程师自测 | — | — | 203 | — |

> 我实测 **200**，工程师 **203**，差 3 —— 疑为其 `rows` 边界（100/101 行）或把表头单元格计入。两者几乎一致，**结论相同：远未达到目标 0**。
> 612 → 200 相比基线 611 降了 67%，说明"去三层描边"做了一半：页面级那一层拆掉了，但表格区那一层还在。

### 3.2 多出来的那一层（实测计算样式）

| 层 | 元素 | border | radius | background | shadow | 高度 |
| --- | --- | --- | --- | --- | --- | --- |
| 最内 | `.wb-button`（每格金额控件） | `1px solid #e2e8f0` | 8px | `#fff` | none | 37px |
| **多出的中间层** | **`.wb-deduction-scroll`** | **`1px solid #e3e6eb`** | **8px** | **`#fff`** | none | 544px |
| 外层 | `.wbx-card.wbx-subview.wbx-deduction` | `0px none` | 12px | `#fff` | `rgba(16,24,40,.06) 0 1px 2px` | 696px |

链路：`wb-button > wb-deduction-scroll > wbx-card.wbx-subview` = **3 层**。
≥3 层节点数正好 **200 = 100 行 × 2 列（安全基金/保险费…）**，即每个单元格的金额控件都在 3 层描边里。

**复现步骤**：薪资核算 → 扣款规则 → 展开「站点例外配置（按需展开，共 154 个匹配站点）」→ 每行金额框向上数 3 层描边容器。

**期望**：`maxChain ≤ 2`、`≥3 层节点 = 0`。**改法**：去掉 `.wb-deduction-scroll` 的 `border + border-radius + background`（描边由外层 `.wbx-card` 提供，滚动区只保留 `max-height + overflow`），即可降到 2 层、200 → 0。
**证据**：`qa-t4/deduction-table-expanded-1440x900.png`（展开后表格整块被包了一层白底圆角框）。
